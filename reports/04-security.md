# 账号/房间/安全工程审查报告（子 agent 原始产出）

审查对象：GDD-PVP.md v0.2。前提：无验证注册、设备长期 JWT、6 位房号是既定产品决策，以下评估的是该决策的风险面与现有缓解是否足够。

---

### [S1] 服务器权威 ≠ 信息隐藏：状态下发未设计按客户端可见性过滤，透视/ESP 可直接摧毁核心玩法
**风险描述**：第 13 节声明"移动、交互、忍耐、进度全部服务端 20Hz 模拟"，但权威只保证数值不可改，不保证信息不可见。全文没有任何一处规定"服务器按玩家可观察范围裁剪下行状态"。对一款核心张力是"隔间门后是玩家、是屎、还是教导主任"的游戏，若服务器把全场实体状态（所有玩家位置、隔间占用者身份与进度、主任 spawn 身份、全部 3D 音源事件）广播给房内所有客户端，改包/内存读取客户端即获得全图透视 + 身份透视 + 全图声呐，嗅闻/口罩/假指示贴这套克制环整体作废。且可见性过滤必须从同步层架构起就设计，上线后补做的成本极高。
**攻击/滥用场景**：1) 内存修改读取实体字段 → 开局即知主任在哪个隔间，嗅闻机制被跳过、撬锁零风险；2) 修改客户端解除 15m 音效半径限制 → 全图音频雷达；3) 第 14 节"视觉声呐"无障碍功能本身就示范了"音频→可视化"的渲染路径，作弊者只需解除其距离/遮挡裁剪即成官方雷达皮；4) 断线重连"快照恢复"若是全量快照，重连瞬间即拉全场状态。
**建议缓解**：把"信息可见性"写进服务器权威的定义：(a) 主任在玩家对其触发闯入/嗅闻校验前，该实体只下发"占用中"，不下发"主任"标记；(b) 隔间内玩家的身份、debuff、排便进度对门外玩家不可见，只按 15m 半径 + 遮挡计算后定向下发声脉冲事件；(c) 音频事件仅发给半径内玩家，视觉声呐只允许渲染已接收的同包数据；(d) 重连快照按"该玩家应知信息"裁剪，非全量；(e) 远处玩家位置降频或不下发（近期无声音/视野接触的实体）。

### [S1] 设备指纹是攻击者完全可控的输入，注册限额/异地检测/加房频控/封禁四道防线全部建在它之上
**风险描述**：2.1 的"同一指纹最多 3 账号"、Refresh 异设备检测，2.2 的"同设备加入限频 5 次/分钟"，12 节的"同设备多账号限制"，全部以客户端上报的指纹为 key。指纹若由客户端计算上报，攻击者每次随机生成即可归零全部限额；主流模拟器（雷电/夜神）原生提供"一键新机"。同时它使封禁逃逸零成本：封号 → 换指纹 → 重新注册，形成永动机。
**攻击/滥用场景**：脚本循环 POST /register，每次携带随机 UUID 作指纹 → 绕过 3 账号上限与 IP 频控（配合代理池）→ 1 小时产出上万账号 → 用于扫房、刷名次分、昵称抢注、辱骂昵称轮换。
**建议缓解**：(a) 指纹改为服务端合成的多维信任分：客户端上报 + 服务端可验证信号（TLS JA3/JA4、HTTP/2 设置帧、时区/语言/屏幕参数聚合、历史行为聚类），任何单一信号不得作为唯一限流 key；(b) 所有限频取 账号、IP 段（/24）、指纹 三维最大值；(c) 注册接口加 PoW（客户端算力证明）或行为验证码，把批量注册成本抬到不经济；(d) 封禁实施多维联封（账号 + 指纹画像 + 奖励回收）。

### [S1] 未成年人合规（实名 + 防沉迷）零设计，属运营前置法定义务
**风险描述**：文档定位 12+、题材为中小学课间，目标用户天然大量含未成年人。若面向中国大陆发行，网络游戏须接入实名认证与防沉迷系统（未成年人限周五六日及法定节假日 20:00–21:00 等），"无手机/无验证注册"与该义务直接冲突；喊话/昵称类 UGC 还叠加内容安全主体责任。这不是可缓解的风险而是准入问题。若出海，COPPA 等年龄门法规同样适用。文档对此只字未提。
**攻击/滥用场景**：非攻击场景，属监管场景：无法取得版号/被投诉下架；未成年人无限制游玩引发监护投诉与舆情。
**建议缓解**：(a) 明确发行辖区并产出合规矩阵；(b) 境内版：手机号实名 + 接入防沉迷验证 + 未成年人时段时长限制；"无验证号"降级为仅可玩教学局/不计名次的体验局；(c) 即便坚持无 PII，也需年龄门与监护人申诉通道；(d) 昵称/喊话内容安全纳入同一评估。

### [S2] 无任何找回因子：忘记密码 = 账号永久死亡；被盗号 = 无救济通道
**风险描述**：注册仅角色名 + 密码，无邮箱/手机。后果一：忘记密码 → 账号内奖励/称号永久丢失（有奖励体系就有账号价值，必有大量客诉）。后果二：账号被盗（token 提取见下条、共享/买卖账号纠纷、钓鱼）后无法证明所有权、无法踢出盗号者、无法重置。昵称抢注与冒充（冒充主播骗房号、冒充官方）也因账号无限再生而无法处置。
**攻击/滥用场景**：骗子在直播间冒称"官方抽奖"收集玩家角色名+密码（或直接骗 30 天 token）→ 改昵称冒充主播 → 引导粉丝进钓鱼房；受害者无任何夺回渠道。
**建议缓解**：(a) 注册成功即强制生成并一次性展示"恢复码"（10–12 位，服务端 argon2id 存储，用于重置密码，使用后重置、7 天冷却），并明示"丢失无法找回"；(b) 提供可选的后期补绑邮箱/手机，绑定后才解锁自助找回；(c) 昵称唯一 + 官方/主播预留名单 + 冒充举报走"强制改名"而非仅封号；(d) 改绑、消耗性资产变动等高敏操作二次确认。

### [S2] Token 生命周期工程缺陷：30 天 Access 无吊销手段、Refresh 轮换未定义、RS256 密钥管理未提
**风险描述**：Access 30d + Refresh 90d 与业界常态（access 5–60min + refresh 单次轮换）差两个数量级。无状态 JWT 被提取（root/备份/抓包/日志泄露）后，若无 jti 黑名单或 token_version，服务端 30 天内无法吊销；"改密码是否回收旧 token"未写；refresh 是否一次性（rotation + 重用检测）未写；RS256 私钥存放与 kid 轮换未写。
**攻击/滥用场景**：从 Android 备份/root 提取 JWT → 用户察觉后改密码，旧 access 仍可用满 30 天；或 refresh 无轮换，盗用一次续 90 天，攻击者低频固定使用即可绕过"异地复用检测"。
**建议缓解**：(a) Access 缩短至 15min–2h，Refresh 30d 且单次轮换：旧 refresh 用过即焚，检测到已焚 refresh 被重用 → 吊销该 token 家族；(b) JWT payload 增加 token_version，改密码/登出全端即令全部旧 token 失效；(c) RS256 私钥入 KMS/HSM，定期 kid 轮换，旧 kid 仅验签不签发；(d) 明文写入文档："修改密码吊销该账号所有 token"。

### [S2] "异地/异设备复用 → 吊销全部 token"将大面积误伤移动端用户；多设备并行策略缺失
**风险描述**：移动端优先的游戏，玩家在 WiFi↔蜂窝↔校园网间切换；运营商 CGNAT 下成千用户共享出口 IP、跨基站即换 IP，基于 IP 的"异地"判定必然误伤。换机/刷机/恢复出厂导致指纹漂移 → 判"异设备" → 吊销 + 强制密码重登，而密码重登恰是本设计唯一恢复手段（叠加上一条无找回 = 连环灾难）。文档也未定义同账号多设备并行策略：按现文逻辑，第二台设备登录/刷新 refresh 就会触发"异设备复用"吊销第一台，平板+手机用户每次切换都要重输密码。
**攻击/滥用场景**：学生在家 WiFi 登录，到校切蜂窝 → 触发吊销 → 强制重输密码 → 忘记密码且无邮箱 → 账号永久丢失。或两台设备互相触发吊销形成乒乓。
**建议缓解**：(a) 异地判定改为"IP 城市/ASN 级 + 多信号投票"（指纹 + IP + 客户端特征），单信号变化仅推送提醒不吊销，多信号同时突变且伴随 refresh 并发使用才吊销；蜂窝 IP 不做地理比对；(b) 指纹变更设 7 天宽限期（旧指纹仍可 refresh 一次完成迁移）；(c) 明文规定并发会话上限（建议 2），新设备登录只踢游戏内会话，不吊销对方 refresh；(d) 吊销动作必须先给用户一个"这是你吗"确认窗口。

### [S2] 房间号 1e6 空间 + 可伪造频控 + 状态差异返回：扫号、狙击、卡房骚扰均成立
**风险描述**：6 位数字仅 100 万空间，1 万活跃房时随机命中率已达 1%；限频 5 次/分钟/设备，但设备可伪造、账号可批量、IP 可代理 → 单设备约 40 分钟扫完全空间，百级指纹节点平均数十秒命中一个活跃房。加入失败的三种返回（不存在/已满/对局中）构成状态 oracle："对局中"= 有 5 人正在打，狙击者蹲结算重入。房间创建侧完全没有频控与并发上限（文档只限了加入）。另外"无房主"结构意味着房间内没有任何踢人/锁房手段，一个恶意占位者即可永久卡死一房（全员准备才开局）。
**攻击/滥用场景**：主播公开房号 → 攻击者脚本扫到该房、第 5 席进入但不点准备 → 开局永远不触发 → 受害者退房重建 → 新房号再次被扫到 → 循环骚扰；或 5 席被 5 个小号抢先占满，真玩家永远进不去。
**建议缓解**：(a) 创建与加入同频控：创建 3 房/小时/账号、并发持有 1 房，按账号+IP 段+指纹三维取 max；(b) 房号仅做路由，加入另需 4 位房主口令（房主可随时换，直播场景口头轮换）；(c) 所有失败返回统一为"无法加入该房间"，对局中房间与不存在同错误码，杜绝枚举；(d) 房号回收后 24h 内不复用，防旧号误入与缓存投毒；(e) 给创建者最小权限：锁房 + 踢人（不破坏服务器托管逻辑）；(f) 第 5 人进入的满员锁定必须服务器原子完成。

### [S2] 多开小号 win-trading 与奖励 farm：同 IP 同房仅"提示"，封禁无牙齿
**风险描述**：同设备 3 号上限被模拟器/伪造指纹绕过（见第 2 条）；12 节"同 IP 同房提示"只给其他人一个提示，不阻止、不减收益。5 人房 1 真 4 假即可稳定第一名 farm 名次分与称号；小号还能拾纸递纸给真号（裁决#2 的 +10 忍耐人情机制直接变成外挂）、集体破罐破摔压缩真号用时。配合无验证注册，被封禁后一分钟重生。
**攻击/滥用场景**：工作室 20 台模拟器各 5 开 → 脚本自动建房互加 → 真号每局带 4 个陪跑 → 折算用时榜全服第一 + 称号批量产出 → 一旦上线排行榜或奖励兑换即成黑产。
**建议缓解**：(a) 服务器强约束：同 IP 段/同指纹聚类的账号不得进入同一房间；若产品要保留好友同玩，走显式"组队房"且整房名次分减半；(b) 名次分/称号发放前置检查：房内任意两账号在 IP 段、指纹、注册时间、历史同房次数上无关联；(c) 风控规则：同组合连续 3 局出现 → 奖励冻结待审、24h 延迟入账；(d) 递纸的人情收益在关联账号之间归零；(e) 封禁升级为画像级联封 + 奖励回收。

### [S2] 观战自由镜头泄露全部隐藏信息；15s 延迟对静态目标不足；AFK 小号 30s 即变免费观察哨
**风险描述**：观战"自由镜头/跟随任一玩家"意味着观战者看到玩家本体看不到的信息（主任身份、各隔间占用者、全场位置）——即使客户端不作恶，观战本身就把第 1 条要防的信息全量下发给了第 6 双眼睛。15s 延迟只防"实时"报点，而本局关键目标高度静态：主任驻留 15–30s、排便 6–14s、占坑者不动，15s 前的情报仍有决定性价值。语音发生在游戏外（连坐组队：5 人局 2 人开黑，一人先完成/送死后开 Discord 报点）。更糟的是挂机判负直接送进观战——小号故意挂机，30 秒后成为队友的尾随摄像头。
**攻击/滥用场景**：A、B 开黑进同房；B 开局不动，30s 判负进观战自由镜头；A 全程收 B 语音："主任刚进隔间 2""C 在 1 号池进度 80%，去打断"。
**建议缓解**：(a) 观战视角改为"跟随对象的客户端视角"（只渲染该玩家本应可见的信息），取消上帝视角；(b) 因 AFK 判负入观战者追加 +60s 延迟，或仅可回看自己的对局/集锦；(c) 观战数据流复用第 1 条的可见性过滤，同一套机制；(d) 同房间存在关联账号（IP/指纹聚类）时，把观战延迟抬高到 ≥ 对局剩余时间；(e) 待定#3（延迟长短）拍板前，先定义观战可见的数据范围。

### [S2] 登录接口无暴力破解/撞库防护；argon2id 高成本哈希本身可被做成 CPU DoS
**风险描述**：角色名即用户名且半公开（昵称/登录名分离只是展示层），密码 ≥8 位，但登录端点未写尝试限频、验证码、锁定策略。可对高价值昵称定向爆破、用常见弱密码跨账号喷洒。同时 argon2id 每次验证都是昂贵计算，无频控时登录接口就是被放大 N 倍的 CPU 消耗点。
**攻击/滥用场景**：脚本抓取榜单昵称 → 对每个名字喷洒 top 弱密码 → 命中即占号改密（且受害者无找回通道）；同时以 1000 QPS 打登录接口 → 全服 CPU 打满。
**建议缓解**：(a) 账号 + IP 段双维限频：单账号 5 次失败/15min 后指数退避 + 图形验证码，连续 20 次锁 24h；(b) 登录 QPS 全局闸门；失败次数升高后降低 argon2id 时间成本参数或要求客户端 PoW；(c) 注册时拒绝 top 10k 弱密码黑名单；(d) 失败提示统一为"角色名或密码错误"。

### [S3] 内容安全与治理闭环仅"举报管道"四个字：审核、封禁、申诉、证据留存全缺；"无 PII"表述不成立
**风险描述**：昵称敏感词过滤是静态单点：谐音、拆字、全半角/Unicode 变体、零宽字符、间隔符均可绕过；改名有冷却但未写"改名重新进审核队列"；快捷喊话轮盘（待定#5）文案未定且无"服务端下发、可下线"的运营设计；举报 → 机审/人审 → 处置分级（警告/禁言/封号/设备封）→ 申诉复核 → 证据留存（对局日志保留多久）整条链路为零。另外"无 PII 是优点"不严谨：设备指纹、IP、JWT 标识在 PIPL/GDPR 下均属个人数据，隐私政策、留存期限、注销删除仍需设计。第 10 节"炸裆集锦可分享"是针对特定昵称玩家的羞辱素材出口。
**攻击/滥用场景**：昵称用变体字符绕过过滤 → 被举报 → 运营无工单系统、无对局日志可查 → 无法定位或误处置 → 申诉无门 → 升级为监管投诉。
**建议缓解**：(a) 昵称审核链：正则黑名单 + 归一化（NFKC、去零宽、全半角折叠、拼音映射）+ 文本机审 API + 人工抽检；改名与新注册同队列；(b) 举报工单最小闭环：举报类型（昵称/挂机/多开/外挂/观战作弊）自动附带对局 ID 与服务器日志切片（保留 ≥90 天）→ 处置等级 → 申诉通道与复核 SLA；(c) 喊话轮盘文案仅服务端下发、客户端不可注入自由文本；(d) 隐私政策明确指纹/IP/JWT 为个人数据及其留存与删除；分享回放提供"隐藏昵称"选项。

### [S3] 宏与行为作弊零检测：按键精灵绕过挂机判定、音频触发自动打断、tick 先到先得把胜负交给 RTT
**风险描述**：挂机判定（15s 无输入→瞌睡，30s→判负）基于"输入存在性"，宏每 10s 发一次摇杆微动即永久豁免；客户端能收到音频情报包（第 1 条）意味着脚本可监听网络事件自动执行打断/推搡。裁决#5"同帧冲突按服务器 tick 序"把抢隔间/打断时机的胜负结构性交给 RTT——低延迟玩家与人为注入延迟（lag switch）者持续占优。另外"客户端本地预测自身移动"未写服务端校验参数（最大速度、单帧位移上限、预测纠偏回弹阈值），存在 speedhack 借纠偏通道注入的口子。
**攻击/滥用场景**：脚本监听"隔壁隔间排便开始"事件包 → 150ms 内自动撬锁/推搡，人类反应无法竞争；或宏号全程微动免判负、只在收益最大时刻出手。
**建议缓解**：(a) 挂机判定改为"输入有效性"：位移熵、交互分布、对局贡献（忍耐消耗/道具使用）综合评分，长期贴地线账号进低奖励池并标记；(b) 同帧冲突不用 tick 到达序，改轮转优先级（每 tick 按玩家 ID 轮换起跑序）或窗口内随机，压缩 RTT 套利；(c) 服务端移动校验成文：速度/位移硬上限，超限回弹并计数；(d) 统计风控：打断反应时间分布（人类 P99 vs 脚本）、无输入期操作精度超阈值进人工复核；(e) 名次分/称号延迟 24h 入账，复核通过后发放。

---

**总评**：3 个 S1 中，两个（可见性过滤、指纹信任模型）是架构级决定，必须在写第一行同步/账号代码前定案；防沉迷合规是发行准入问题需要产品层拍板。无验证注册 + 长期 JWT 本身可以做成（等价于游客账号 + 恢复码模式），但当前文档的缓解措施（指纹限额、异地吊销、加入频控、同 IP 提示）全部依赖攻击者可控的单一信号，等于没有缓解；建议把"恢复码 + 短 access + refresh 轮换 + 三维频控 + 服务端可见性过滤"作为这五项的最低落地标准写入 GDD v0.3。
